# 法官資料分析

臺北地院民事判決的法官層級分析。與爬蟲／解析程式分離，確保職責清楚：
**結構化規則一律寫在專案根目錄的 `structuring.py`，本資料夾只做分析，不做推導。**

---

## 快速開始

```bash
# 1. 先把結構化欄位寫進資料庫（只需在規則變動後執行）
python backfill_structured.py --court 臺北 --year 2025

# 2. 跑分析
python judge_analysis/run_analysis.py
```

產出在 `judge_analysis/output/`：

| 檔案 | 內容 |
|---|---|
| `judge_profile.csv` | 每位法官一列：案件數、勝訴率、期望勝訴率、差異、p 值 |
| `judge_case_mix.csv` | 法官 × 案由大類 的案件數（誰在辦什麼案子） |
| `judge_outcome_by_casetype.csv` | 法官 × 案由大類 的勝訴率 |
| `judge_law_preference.csv` | 法官 × 法規 的引用次數 |
| `panel_stats.csv` | 合議庭組合與其結果分布 |
| `judge_analysis.xlsx` | 以上全部整合成一份活頁簿 |

## 方法論：為什麼不能直接比勝訴率

法官手上的案件組合不同。專辦清償借款（銀行告債務人、證據明確）的法官，
原告勝訴率天生就高於專辦侵權損害賠償的法官。這個差距來自**案件分派**，
不是心證。直接比較原始勝訴率會把分派差異誤讀成法官傾向。

因此 `judge_profile.csv` 算的是**案件組合調整後的差異**：

```
期望勝訴數 E = Σ（每個案件所屬案由大類的全體平均勝訴率）
實際勝訴數 O
差異 = O − E
```

再以常態近似計算雙尾 p 值，並用 **Benjamini–Hochberg** 控制偽發現率。
不校正的話，86 位法官在 α=0.05 下平均會有 4 位純靠運氣「顯著」。

### 三個必須寫進結論的但書

1. **這不是因果推論。** 差異也可能來自案件分派並非隨機（複雜案件可能
   集中分給資深法官）。要排除這點，需要知道分案規則或使用分案的隨機性。
2. **合議庭案件會被計入 3 位法官。** 這在「參與過哪些案件」的問題下正確，
   但不等於「該法官獨自決定」。要做最乾淨的個人傾向比較，請只取
   `role == '獨任'` 的子集。
3. **單一年度、單一法院。** 2025 年臺北地院一年的資料，每位法官約 30–240 件。
   結論不能外推到其他年度或法院。

## 欄位字典

分析所需欄位分四層。**L1–L3 已由 `structuring.py` 實作完成**；
L4（心證層）是另一位同學負責的範圍，規格列於下一節。

### L1 法官身分層

| 欄位 | 說明 |
|---|---|
| `judges` | 原始法官欄位，**以全形分號 `；` 分隔**（用頓號切會完全失效） |
| `judges_json` | `[{name, role, seat}]`；`role` ∈ 獨任／審判長／陪席 |
| `presiding_judge` | 審判長或獨任法官，案件層級分析的法官維度 |
| `judge_count` | 法官人數，>1 即為合議庭 |
| `panel_key` | 合議庭組合鍵（姓名排序後串接），用來看誰常同庭 |

> **不推定「受命法官」。** 判決書簽名欄只標示審判長，不標示受命法官。
> 任何推定都是捏造，寧可留白。

### L2 案件特徵層（控制變數）

沒有這一層就無法區分「法官傾向」與「案件難度」。

| 欄位 | 說明 |
|---|---|
| `case_kind` / `case_kind_category` | 字別（訴、重訴、除…）與層級（給付確認／非對審／上訴抗告／家事形成／裁定） |
| `case_type_norm` / `case_type_category` | 案由正規化（717 種）與大類（17 類） |
| `claimed_amount` + `claimed_source` | 請求金額與其**來源**（見下方警告） |
| `defendant_is_corp` | 被告是否為法人 |
| `plaintiff_has_lawyer` / `defendant_has_lawyer` | 兩造是否有律師 |
| `is_default_judgment` | 是否一造辯論判決 |
| `reasoning_length` | 論理字數＝`reasons`＋`facts_and_reasons`＋`facts`（三者擇一撰寫，相加才是完整論理長度）|

#### ⚠ 解讀 `*_has_lawyer` 的兩個前提

- **`0` 的意思是「判決書上看不出代理人是律師」，不是「沒有律師」。**
  判準是拿代理人姓名回全文比對後方是否緊接「律師」；判決只寫
  「訴訟代理人 王大明」而未註明身分時會判 0。這個欄位可以當控制變數，
  但不能當成律師代理率對外引用。
- **`被告有律師比例` 與 `一造辯論比例` 高度相關（r = -0.68，對審 ≥ 30 件的
  73 位法官）。** 被告未到庭當然沒有律師——一造辯論案件中 94.4% 的
  `defendant_has_lawyer` 為 0。比較法官的「被告有律師比例」時，讀到的
  有近半是他的一造辯論比例，兩欄不宜同時放進同一個迴歸。

### L3 判決結果層（依變數）

| 欄位 | 說明 |
|---|---|
| `outcome` | 訴訟結果，**僅在 `case_kind_category == '給付確認'` 時有值** |
| `main_outcome` / `counter_outcome` | 本訴／反訴分離 |
| `appeal_outcome` | 上訴審結果（上訴駁回／原判決廢棄／一部廢棄） |
| `relief_type` | 給付類型（金錢給付／非金錢給付／確認／形成／不作為） |
| `awarded_amount` + `awarded_currency` | 判准金額（全部判項加總）與幣別 |
| `grant_ratio` | 獲償比例＝判准／請求 |
| `cost_share_plaintiff` | 訴訟費用原告負擔比例 |
| `law_primary` / `applicable_laws_json` | 主要法規與結構化法條引用 |
| `quality_flags` | 品質旗標，見下 |

#### ⚠ 使用 `grant_ratio` 前必讀

`claimed_source` 有三種值：**直接抽取 / 主文回推 / 未取得**。

「主文回推」是指聲明寫「如主文所示」且全部勝訴時，用判准金額代入請求金額。
這類資料的獲償比例恆為 100%，拿去算平均會嚴重高估法院的准許程度，
屬於循環論證。**`grant_ratio` 只在 `claimed_source == '直接抽取'` 時才有值**，
程式已經強制這一點，但做自訂分析時請自己再確認一次。

同理，`cost_share_plaintiff` 是比 `outcome` 更精細的連續變數：
主文只說「一部勝訴一部敗訴」，但「訴訟費用由被告負擔 97%」和「負擔 3%」
是天差地別的結果。做寬嚴比較時它比三分類的 `outcome` 有用得多。

#### `quality_flags` 的值

| 旗標 | 意義 | 分析時怎麼辦 |
|---|---|---|
| `金額於附表` | 金額寫在附表，正文抓不到 | 從金額分母排除，或人工補 |
| `非金錢給付` | 本來就沒有金額 | **不是缺漏**，從金額分母排除 |
| `定期給付` | 按月／按年給付，沒有總額 | 同上，本質上不存在總額 |
| `外幣` / `混合幣別未合計` | 非台幣或多幣別 | 不做匯率換算，單獨處理 |
| `判准大於請求` | 聲明段落只抓到部分項目 | `grant_ratio` 已作廢，勿自行回推 |
| `重複給付免責` | 不真正連帶：主文分列數判項，但有「任一被告給付後其餘免責」條款，各判項是同一筆債務 | `awarded_amount` **刻意留空**（加總會憑空多一倍）；需要時看 `awarded_items_json` 自行判斷，勿逕行加總或去重 |
| `金額抽取失敗` | 真正的抽取失敗 | 這才是需要改進規則的部分 |
| `無法條引用` / `無法官` | 上游解析缺漏 | 從相關分析排除 |

## L4 心證層規格（交接用）

以下是**尚未實作**的欄位規格，供負責心證分析的同學參考。
每一項都附上抽取位置與建議規則。

### 4.1 爭點

| 欄位 | 型別 | 抽取規則 |
|---|---|---|
| `issues[]` | list[str] | 理由段落中「兩造爭執之處」「本件爭點厥為」「爭點如下」之後到下一個編號標題之間的內容，依編號切分 |
| `n_issues` | int | 上者的長度 |

### 4.2 證據

| 欄位 | 型別 | 抽取規則 |
|---|---|---|
| `evidence_types[]` | list[str] | 以詞典比對理由段：書證／證人證述／鑑定／勘驗／當事人訊問／錄音錄影／LINE 對話／監視器／診斷證明／公文書／函詢 |
| `evidence_credited[]` | list[{type, credited}] | 在每個證據詞的 **±40 字**視窗內掃描評價詞：<br>採信 = 堪信／可採／足認／應堪採信／非虛<br>不採 = 不足採／無可採／不可採／難認／尚難／無足取 |
| `expert_opinion` | 0/1 | 是否出現「鑑定報告」「鑑定意見」 |

> 這是全部欄位中**最容易做錯**的一項。±40 字視窗會跨到相鄰句子，
> 必須以句號切分後再取視窗，且要處理「雖…堪信…然…不足採」這類轉折。
> 建議先寫驗證腳本跑全量、抽樣 50 筆人工核對，再寫進正式程式
> ——這是本專案既有欄位一路採用的流程。

### 4.3 舉證責任與心證強度

| 欄位 | 型別 | 抽取規則 |
|---|---|---|
| `burden_of_proof_cited` | 0/1 | 是否引用民事訴訟法第277條，或出現「舉證責任」 |
| `burden_allocated_to` | str | 「應由原告／被告負舉證責任」的受詞 |
| `conviction_strong` | int | 「堪認」「足認」「應堪認定」出現次數 |
| `conviction_weak` | int | 「難認」「尚難認定」「顯有疑義」「不無疑問」出現次數 |
| `cited_supreme_court[]` | list[str] | `最高法院\d+年度台上字第\d+號` 的全部出現 |
| `cited_precedent_count` | int | 上者去重後的數量 |

### 4.4 建議的分析設計

有了 L4 之後，即可回答：

- **「法官是否對特定類別總是採用特定證據？」**
  `judge × case_type_category × evidence_type` 的條件機率，
  與全體基準線比較後做卡方檢定（同樣要 BH 校正）。

- **「法官是否總是判特定結果？」**
  以 `outcome` 為依變數、`judge` 為固定效果，
  控制 L2 全部變數後跑 logistic regression。
  目前環境沒有 statsmodels/scipy，需先 `pip install statsmodels`。

- **「法官對某類證據的採信率是否異於同儕？」**
  `evidence_credited` 攤平後，以法官為分組計算採信率，
  並以案件組合調整（做法與 `metrics.judge_profile` 相同）。

## 重現性

本資料夾的所有數字都可以從 `judgments.db` 重新產生：

```bash
python -m unittest discover -s tests -t .      # 規則的回歸測試
python backfill_structured.py --dry-run        # 確認規則產出的分布
python backfill_structured.py                  # 寫入（會自動備份 DB）
python judge_analysis/run_analysis.py          # 產生報表
```

規則版本記錄在每一列的 `structuring_version` 欄位。規則改版後，
`backfill_structured.py --only-missing` 會自動把舊版本的列刷新，
不會留下混版資料。
