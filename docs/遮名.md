# 遮名

平台會顯示真實判決的內容（相似判決、判決導讀），也會把使用者的描述送給模型和 LLM。這份文件說明哪裡會遮名、怎麼遮、怎麼量測漏遮率，以及重建檢索資料的步驟。

## 要遮到什麼程度（2026-11-13 查證）

> 以下是組內整理的法律資料，不是法律意見；第 3 節標「未查到原文」的案例只能當參考。分級標準是本平台自己訂的目標，請組內（含法律背景的同學）確認。

### 1. 結論

- **法律只規定法院自己公開判決時要遮什麼，沒有規定別人再利用判決時要遮到什麼程度。** 再利用依個資法的一般原則，看「利用目的、方式、是否超出必要」個案判斷，沒有百分比或數字門檻。
- 法院審理轉貼判決的案件時，看的是目的（教育、公共利益，還是公審、報復）、呈現方式（中性，或加上貶損評論、聳動標題）、揭露程度（有沒有露出身分證、地址等法院本來就不公開的資料）。
- 本平台的用途是法律資訊與教育，呈現中性，遮得比司法院還多，並附司法院原文連結，屬於低風險的利用方式。真正要守住的是**法律明文不公開的資料**（身分證、出生年月日、地址），不能由我們重新露出；姓名是平台額外的保護，用自訂的漏遮率目標管理。

### 2. 法律規定

| 規定 | 內容 | 對本平台的意義 |
|---|---|---|
| 法院組織法第 83 條第 2 項 | 裁判書公開時「除自然人之姓名外，得不含自然人之身分證統一編號及其他足資識別該個人之資料」 | 姓名本來就公開；司法院網站上的民事判決，當事人姓名通常完整顯示（抽查 113 年度訴字第 6370 號） |
| 法務部 104.01.30 法律字第 10403501320 號函 | 裁判書公開以姓名公開為原則，不含身分證統一編號、護照號碼、出生年月日、地址；資料取自合法公開的裁判書，非公務機關仍要依個資法第 19 條逐款判斷能否蒐集、利用 | 「已公開」不等於可以任意使用，要有正當目的 |
| 個資法第 19、20 條 | 非公務機關蒐集、處理個資要符合特定目的與法定要件；利用要在目的的必要範圍內 | 平台的目的（法律資訊）要說得清楚，不揭露超過需要的資料 |
| 個資會籌備處 114.07.15 個資籌法字第 1140000771 號函 | 去識別化後，若客觀上仍能還原、間接識別當事人，利用時仍適用個資法 | 遮掉名字不代表完全沒有個資問題，所以要量測並說明限制 |
| 個資法第 28 條第 3 項 | 民事賠償每人每一事件新臺幣 500 元以上 2 萬元以下（無法證明實際損害時） | 違規代價的參考 |

### 3. 可參考的判決與見解

| 案件或見解 | 內容 | 和本平台的關係 |
|---|---|---|
| **臺北地院 108 年度北再小字第 4 號**（再審） | 立委在臉書張貼判決節錄與司法院連結，原判決（107 年度北小字第 3421 號）認定違反個資法、賠 1 萬元；再審推翻，理由是「法院裁判書內容既屬政府應公開之資訊，任何人均得自由取得其內容加以瞭解」，附司法院連結「並無違反社會常情」，即使不附連結，「第三人均得自司法院網站中搜尋相關實務見解」 | 和「顯示遮名版＋附原文連結」最接近，而且我們還多遮了姓名 |
| 臺灣高等檢察署〈判決書貼上網，名字打O就可以嗎?〉 | 把判決貼上網屬於個資的「利用」；裁判書公開「不是要提供給訴訟當事人，作為公審他人、網路霸凌之用」；名字打 O 不一定夠，職業、家庭關係等能比對出特定人時仍是個資 | 偏嚴格的官方立場；重點在目的，本平台不針對任何個人 |
| 施先生 v. Google（被遺忘權） | 一審認為被遺忘權不是現行法承認的權利；二審認為資訊隱私是憲法上的權利，但要和公眾取得資訊的公共利益權衡 | 公開資訊的再利用是權衡問題，不是當事人要求就一定要下架 |
| 憲法法庭 111 年憲判字第 13 號（健保資料庫案） | 公務機關把個資提供給第三人做其他用途，要有法律明文依據；也指出缺少當事人請求停止利用的機制 | 對象是政府機關，不直接適用本平台；但「目的外利用要有正當基礎、要讓當事人有管道」的精神一致 |
| 判賠案例（**未查到原文**，來自律師事務所與新聞整理） | 轉貼判決時搭配聳動標題、刻意凸顯身分，判賠 5 萬到 8 萬元；把未遮身分證字號的判決寄給社區住戶，判賠每人 5 千元 | 共同點是惡意、加上評論，或露出法院本來就不公開的資料；本平台要避免的是後者 |

### 4. 本平台的做法對照

| 法院看的因素 | 本平台 |
|---|---|
| 利用目的 | 讓民眾了解類似案件的判決結果，屬於法律資訊與教育，不針對任何個人 |
| 呈現方式 | 中性，沒有評論，不會標出或排序特定人 |
| 揭露程度 | 比司法院還少：當事人、第三人姓名換成角色代號，車牌、電話、地址也遮 |
| 法律明文不公開的資料 | 身分證、出生年月日、有門牌的地址，1,000 件自動檢查都是 0（見第 6 節） |
| 取得原文 | 相似判決與導讀附司法院原文連結（2026-11-13 起），想看完整判決的人到原處看 |
| 當事人的管道 | 還沒有，見第 7 節 |

### 5. 本平台的分級標準

| 類別 | 標準 | 理由 |
|---|---|---|
| 身分證字號、出生年月日、有門牌的地址 | 抽查 0 件 | 法律規定法院公開時不含這些資料，我們不能比司法院揭露得更多 |
| 自然人姓名（當事人、第三人） | 至少一個名字漏遮的判決在 5% 以下（95% 信心） | 法律上姓名可以公開，遮名是平台額外的保護；附原文連結，要看完整版本的人可以去原處看 |
| 車牌、電話、帳號、病歷號等 | 盡量遮，抽查時一起記錄 | 可以連到特定人，但出現的頻率低 |

「95% 信心下 5% 以下」的意思：重建後隨機抽 60 件逐字讀，0 件漏遮，就能說漏遮的判決比例有 95% 的把握低於 5%（抽 n 件、0 件漏遮時，上限約為 3 / n，統計上稱為「三法則」）。抽 30 件只能說低於約 10%，抽 100 件可以說低於 3%。

國外的對照：德國用自動遮名產生法院判決的官方公開版本，研究目標是召回率接近 99%，因為它們的遮名版就是唯一公開的版本。本平台的原文本來就在司法院網站上，所以姓名採較寬的 5% 目標。另一份和瑞士聯邦最高法院合作的研究發現，即使是能力最強的大型語言模型，也很難從已匿名的判決裡認出當事人。

### 7. 待組內確認

1. 第 5 節的分級標準，特別是姓名的 5% 目標。
2. 法官、律師、引用的學者這類公開身分的名字要不要遮（目前人名辨識找到的都會遮）。
3. 只有名字沒有姓（「怡文打人了」「宛臻再婚」）和暱稱（「阿茂」「小胖」）目前不遮：這類名字不以姓氏開頭，無法用出現件數判斷，做全文取代容易誤遮一般用語，而且單獨的名字認不太出是誰。
4. 是否提供當事人申請移除或加強遮蔽的管道（例如在隱私說明頁附聯絡方式），可以和 A4 的隱私說明頁一起處理。
5. 請法律背景的同學確認第 2、3 節，特別是未查到原文的判賠案例。

### 名詞

- **去識別化**：把資料處理到無法直接或間接認出特定個人。遮名是其中一種做法。
- **再識別**：從去識別化的資料，透過比對其他資訊重新認出是誰（例如由職業、地點、事件細節推出當事人）。
- **召回率**：該遮的資訊裡實際遮到的比例。漏遮率＝1－召回率。
- **人名辨識（NER）**：命名實體辨識，自動找出文字裡的人名、地名、機構名。本平台用中研院 CKIP 的模型。
- **三法則**：抽查 n 件都沒有發現問題時，問題的真實比例有 95% 的把握低於約 3 / n。

## 哪裡會遮

| 文字 | 在哪裡遮 | 程式 |
|---|---|---|
| 使用者的描述 | 瀏覽器（原文不傳到伺服器）；送給 LLM 前，後端再遮一次 | `frontend/src/mask.ts`、`retrieval/masking.py` 的 `mask()` |
| 民事判決（相似判決、導讀） | **建檢索資料時**遮好，存進 `cases.sqlite`，網站執行時不再處理 | `retrieval/build.py` → `masking.mask_parties` |
| 刑事判決（相似判決） | 建檢索資料時遮好 | `retrieval/criminal.py` 的 `masked()` |

`mask()` 是三條路共用的規則：身分證字號、電話、電子郵件、有門牌號碼的地址（有沒有寫縣市都遮）、出生年月日，以及車牌。`mask.ts` 和 `mask()` 規則要一致，兩邊跑同一份測試案例 `frontend/src/test/masking_cases.json`。

## 每個環節對到的檔案

**使用者的描述（網站執行時）**

| 步驟 | 檔案 |

## 民事判決怎麼遮

1. **當事人**：用判決的原告、被告、代理人欄位，換成【原告】【被告】【代理人】。
2. **有稱謂的第三人**：「訴外人」「證人」「之子」「繼承人即」等稱謂後面接常見姓氏的，換成【關係人】（`third_party_names`）。整件判決找到的名字，在每一段都會換掉。
3. **沒有稱謂的人名**（2026-11 新增）：用 CKIP 的人名辨識（`retrieval/ner.py`）事先找出來，篩過之後（`usable_person_names`）和第 2 步一樣換成【關係人】。

**多人時編號**（2026-11 新增）：同一個角色只有一個人時是【被告】；有多人時依序編號【被告1】【被告2】、【關係人1】【關係人2】，否則「【關係人】向【關係人】借款」分不出誰是誰。當事人依當事人欄位的順序編號，關係人依在判決裡（原告主張、被告答辯、法院判斷）第一次出現的順序編號；同一件判決的三段與摘要用同一份名單，同一個編號一定是同一個人。前端用通用的「【…】」規則標橘色，不受編號影響。
4. **其他個資**：`mask()`。

司法院公開判決時已經把一部分人名遮成「王○明」、車牌遮成「000-0000」，這些不用再處理。

### 為什麼人名辨識只在建資料時跑

CKIP 是 BERT 模型，需要 torch，有 GPU 才跑得快。判決在建資料時遮一次就好，網站和部署環境不用裝這個模型，Docker 映像也不會變大。使用者的描述在瀏覽器遮，同樣放不進這種模型，所以使用者要在預覽時自己補上名字。

### 篩掉的辨識結果

人名辨識的結果會在整件判決裡做取代，誤判會把一般用語一起遮掉。所以以下結果不拿來用：

- 不是 2–4 個中文字的（中文字包含 Unicode 擴充區的罕用字：人工抽查發現「陳奕𤋱」因為「𤋱」不在常用字範圍而漏遮）
- **兩個字的，只有在全部判決裡很少出現（10 件以內）時才遮**（`rare_two_char_names`，2026-11-14）。人工抽查發現「馬達」被當成人名遮掉；兩個字的辨識結果很多是一般詞，而一般詞會出現在很多判決裡、人名通常只有一兩件，用出現的件數分開：

  | 類型 | 15.8 萬件裡出現的件數 |
  |---|---|
  | 一般詞 | 陳明 43,340、陳情 1,016、馬達 687、周全 204、周旋 111 |
  | 兩個字的全名 | 劉旭 3、張蕾 2、魏莉 2、許軒 2、王鑫 1 |

  另外兩個字的還要以常見姓氏開頭，第二個字不能是數字（「張一」會把「主張一部」也遮掉）或常見大姓（「王陳」「劉李」）。少數很少見的一般詞另外列出（「卓見」「毛遂」「余裕」）。只建一部分判決（抽查）時，件數要用全部判決算好傳進去（`write_artifacts(rare_two_char=...)`）
- 四個字的去掉黏上的字：「經查張德滿」辨識出的「查張德滿」→「張德滿」，「王怡文固」→「王怡文」；成語、外來詞另外列出（「張冠李戴」「烏克麗麗」）
- 判決用語黏上去的（「利云云」「固可認」「卷可佐」「伊前夫」，以及「主張渠等」切出的「張渠」）。「云」本身不排除，「曾湘云」是真名，只排除含「云云」的；「之、渠、其、開」也不一律排除（「張之瑋」「吳渭渠」「陳其邁」「儲開軒」是真名），只排除以「之」結尾（「余梅之出資」）、兩個字且第二字是「伊、渠、其」、以「上」開頭（「上開二」）的
- 親屬稱謂接姓氏的兩個字（「之孫鄭維德」辨識出的「孫鄭」）
- 法院給未成年人或匿名者的代稱：兩個字、第二個字是「童、姓、某、氏、男、女」的（「蘇童」＝姓蘇的兒童、「王姓」「陳某」），本來就認不出是誰
- 已經遮過的（含「○」），以及「陳述」「簡易」這類常見詞開頭的
- 計算方法的名稱（「霍夫曼」）

**有「伊」的名字**（2026-11-14 改）：「伊」在判決裡常是代名詞（他、她），原本名字裡有「伊」的一律不收，但人工抽查發現「志伊玲華」因此漏遮。查全部 15.8 萬件的辨識結果，只因為「伊」被擋掉的有 422 種，其中很多是真名（黃伊弘、謝伊婷、林芷伊、莊喬伊）。現在的判斷（`_yi_name_ok`）：

| | 代名詞（不遮） | 名字（遮） |
|---|---|---|
| 例子 | 約定伊、陳稱伊、斯時伊、伊及伊、明知伊 | 黃伊弘、謝伊婷、林芷伊、呂致伊 |
| 第一個字 | 不是姓（約、斯、明），或是「伊」 | 姓 |
| 「伊」的前後 | 動詞或虛詞（稱、知、定、時、因、及、與、說、請） | 名字用字 |
| 「伊」在第三個字以後時的前兩個字 | 一般詞：金錢 60,095 件、程序 144,976 件、陳稱 15,444 件 | 人名開頭：林芷 167 件、陳韻 767 件、莊喬 41 件 |

前兩個字出現在 1,000 件以上的判決就當一般詞（`COMMON_MIN_DF`，`name_word_frequencies` 和兩個字的名字一起算，只讀一次語料）。四個字、最後一個是「伊」的，是三個字的名字接代名詞（「蔡如滿伊」→「蔡如滿」），複姓除外（「歐陽芷伊」）；剪掉「伊」或「嗣」以前要先看第一個字是不是姓，不是的整個不收（「茲陳報伊」「不爭執伊」「非約定伊」「鏡週刊嗣」剪完是一般詞）。姓開頭的動詞接「伊」（「羅織伊」「杜撰伊」）另外列在 `_YI_VERBS`。

第一次重建後比對新遮掉的字串才發現上面這兩類誤遮（9 種），補上後和前一版相比，只有這 9 種不再遮，另外多遮一個「黄伊平」（姓氏表補了異體字「黄」「温」和凌、戚、柴、闕等較少見的姓）。

不收的：「志伊玲華」這種不在姓氏表裡的複姓（四個字裡哪幾個是姓分不出來），以及不在 `_YI_VERBS` 裡、出現次數又不多的動詞接「伊」（「羅織」只有 116 件，次數分不出來，只能一個一個列，屬於多遮）。

### 取代的順序與名單補抓

- 一件判決裡所有要遮的名字（原告、被告、代理人、關係人）合在一起，**長的先全部換掉，再換短的**。原文「曾孫鄭宇峰」裡，誤判的「孫鄭」如果先換，會切斷「鄭宇峰」、露出「宇峰」。換的時候先放私用區的記號，全部換完才換成標籤，短的名字才不會換到已經放好的標籤裡（人工抽查發現「【被告】」裡的「被告」又被換掉，變成「【【代理人3】】」）。
- 當事人欄位裡的角色詞不當名字：資料庫的代理人欄位有時解析成「被告兼下一人；陳晁遠」（原文是「被告兼下一人之法定代理人 陳晁遠」），清掉「兼…」後只剩「被告」。現在角色詞會被排除，而且寫明是原告或被告的人歸到當事人（`party_roles`）：陳晁遠是【被告2】，不是代理人。
- 列舉裡夾在已知名字之間的名字也遮（`listed_with`）：「【關係人80】、吳渭渠、【關係人83】」原文是一串人名，人名辨識漏掉其中一個時，靠前一個已知的名字補上。
- 稱謂另外加了「友人、朋友、同事、鄰居、女友、男友、前妻、前夫、同居人、房東、房客、之孫、曾孫、孫女、孫子」（「友人杜英達」）。
- 兩個字的姓（2026-11-14）：「頴川建忠」的次子「頴川欽和」，人名辨識在某些句子只抓到「川欽和」，遮完留下「頴【關係人1】」。同一件判決裡已經有四個字的名字以「頴川」開頭時，「頴」＋「川欽和」也用同一個標籤。

## 地址

兩條規則：

1. 從縣市開始的完整地址（「臺北市大安區和平東路二段106號3樓」）。
2. 沒寫縣市、但有門牌號碼的地址**一律遮**（2026-11-13 起）：「中庄街71巷56號」「永靖鄉同安村永福路1段664號」。原本考慮只在前後有「門牌號碼」「房屋」等詞時才遮，但「承租富宜路270號」「不動產所在地：楊梅鎮高獅路711號」這類寫法會漏掉。代價是車禍地點也會遮（「停於【地址】前」），句子仍讀得懂。

只有路名、沒有門牌號碼的不遮（「沿中山路往南行駛」）。路名不能從虛詞或動詞開始，否則會把前面的字吃掉：單字擋「時、於、在、到、寄、沿」等幾乎不會出現在路名裡的字；「經、由、前、開」可能是路名（經國路、自由路、前鎮區、開元路），只擋判決常見的詞（「經查」「由於」「之前」「當時」），詞的第二個字也擋（「經查中山路5號」不會變成「經【地址】」）。

使用者的描述也套用同樣的規則（`mask.ts`），以前「住大安區和平東路106號」這種沒寫縣市的地址要使用者自己補遮，現在會自動遮。

## 出生年月日

「89年4月6日生，」「民國41年1月15日出生。」「46年6月29日生之原告」換成【出生日期】。後面要接標點、括號、「之及於等至」、「現年」「當時」「計至」或結尾才遮（「59年12月31日生當時30歲」「67年1月27日生等情」；這幾種是第二次重建後全量檢查找到的，約 10 件），「自112年1月4日生送達效力」「…日生效」不會被遮。法院公開時通常已經寫成「00年0月00日生」，但 1,000 件裡有 3 件沒遮。

## 車牌

一看就是車牌的格式直接遮：汽車 `ABC-1234`、`AB-1234`、`1234-AB`，機車 `ABC-123`、`123-ABC`。其他格式（`AB-123`、法院遮過的 `000-0000`）要前面寫了「車牌」「車號」「牌照」才遮。

沒有連字號的（2026-11-14，全量檢查發現）：前面是「機車、車輛、汽車、貨車、小客車、車斗、拖車、牌號」時才遮，英文字母和數字都要有（「機車FBL922」「車輛ARK6316號」「牌號EQE3228」）。「車輛2023年」不會遮；型號（「引進GLE350的車子」）前面不是這些詞，也不會遮。

前後接著英數字或「-」的不遮，所以 `7345-ST-A03` 這類圖號不受影響。`ISO-9001` 這類標準編號也不遮。在 7,872 件判決上試過：嚴格格式找到 217 個，約 5 個是誤判（工程項次 `DCN-028`、`SOP-201`），其餘都是車牌。

## 量測漏遮率

```bash
# 1. 從上線用的檢索資料抽 200 件，匯出標註表（存在 data_masking/，不進版控）
python -m retrieval.masking_audit sample --out data_masking/audit_1.xlsx

# （可選）先跑人名辨識，把還沒遮掉的人名列在提示欄
.venv-ner/Scripts/python -m retrieval.ner --out data_masking/ner_audit_1.jsonl --ids-from data_masking/audit_1.xlsx
python -m retrieval.masking_audit sample --out data_masking/audit_1.xlsx --ner-names data_masking/ner_audit_1.jsonl

# 2. 人工標註：每列讀完，把漏遮的姓名、車牌、身分證、地址填進對應欄位（表裡的「說明」工作表有規則）

# 3. 算漏遮率
python -m retrieval.masking_audit score data_masking/audit_1.xlsx

# 4. 改完遮名、重建檢索資料後，抽另一批（不和第一批重複）再量一次
python -m retrieval.masking_audit sample --out data_masking/audit_2.xlsx --exclude-from data_masking/audit_1.xlsx --seed 2
```

`score` 會列出每一類的：有問題的件數、個數（同一件判決同樣的名字只算一次）、每 100 件幾個。「誤遮」欄另外算，用來看遮太多的代價。

## 重建民事檢索資料

```bash
# 1. 人名辨識（RTX 4060 約 8 小時；可以中斷，重跑同一個指令會接著跑）
.venv-ner/Scripts/python -m retrieval.ner --out data_masking/ner_civil.jsonl

# 2. 重建（會檢查人名辨識的結果是否涵蓋所有判決）
python -m retrieval.build --ner-names data_masking/ner_civil.jsonl

# 3. 上傳到 HF：遮名或內容有改就換新的資料夾名稱（retrieval_civil_v5…），改 retrieval/build.py 的 NAME，見 docs/資料版本.md、docs/模型檔上傳.md
```

兩個步驟都會讀整份正式資料庫（`judgments.db`），**爬蟲在跑的時候不要執行**，不然爬蟲會遇到 database is locked。重建時會用當下的資料庫，件數可能和上一版不同，上傳時在 commit message 寫清楚。

`.venv-ner` 的建法見 `retrieval/ner.py` 開頭。CKIP 模型檔是舊的 `.bin` 格式，搭配 transformers 4.56 時，torch 要 2.6 以上才能讀。
