# 資料庫欄位說明

`judgments.db` 各資料表與欄位的說明：每個欄位**是什麼、怎麼來的、為什麼需要**。
用 `python browse_db.py`（Datasette）瀏覽資料庫時，可以對照這份文件。

- 民事與刑事判決都存在同一張 `judgments` 表。標記 **【民事】** 的欄位由民事結構化規則
  推導。這套規則對刑事判決也會執行，所以刑事判決的這些欄位**可能有值，但沒有意義**
  （例如刑事判決被歸為「給付確認」、標成「勝訴」）。**分析刑事判決時請忽略【民事】欄位。**
- 刑事的罪名、法條、刑度目前另有兩條產出路徑，見[刑事相關資料](#刑事相關資料)。
- 分析這些欄位前，請先讀[使用注意事項](#使用注意事項)。這份文件與程式衝突時，
  以程式（`structuring.py`、`html_parser.py`）的實際行為為準。
- **新增或修改欄位、改推導規則時，請一起更新這份文件。**

## 資料表一覽

| 資料表 | 內容 | 什麼時候看 |
|---|---|---|
| `judgments` | 一列一份裁判書：解析出的欄位（法院、當事人、主文、理由、法官…）與結構化欄位（案件類型、勝敗、金額、法條…） | **平常看這張就好** |
| `crawl_records` | 爬取紀錄：網址、存在 `html_cache/` 的檔名、第一次被哪個批次抓到、是否已解析 | 除錯或追查資料來源時 |
| `offenses` | 刑事判決附表的「被告 × 罪 × 宣告刑」，執行過 `build_offenses.py` 才會有 | 刑事分析 |
| `sqlite_` 開頭的表 | SQLite 自己用的內部資料表 | 不用理會 |

> 用 Datasette 瀏覽時，首頁最大的「judgments」是**整個資料庫檔案**（`judgments.db`），
> 點進去才會看到上面這些資料表。資料庫檔案和最主要的資料表剛好同名，別搞混了。

## judgments 表

### 識別與來源

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `id` | 資料列編號（自動遞增） | 資料庫內部主鍵。`html_parser.py --reparse` 會清空重建，編號會全部改變，**不要拿來當長期識別碼**——長期識別請用 `case_number` |
| `crawl_id` | 對應 `crawl_records` 表的 `id` | 由這筆解析結果追回原始 HTML 檔與爬取紀錄 |
| `case_number` | 裁判字號，如「臺灣臺北地方法院 114 年度 訴 字第 123 號民事判決」 | 一份裁判書的唯一識別，跨資料庫合併、去重、引用個案都用它 |
| `court` | 法院全名。分院與地方庭中間有空格（「臺灣高等法院 臺中分院」） | 依法院分組比較。要把高院與各分院一起看時用 `LIKE '臺灣高等法院%'` |
| `judgment_date` | 裁判日期，西元 `YYYY-MM-DD` | 統一格式後可以直接排序、做日期區間篩選 |
| `case_type` | 案由原文，取自裁判書開頭的「裁判案由」（如「清償借款」「損害賠償等」「詐欺」） | 起訴方主張的爭議類型，民事與刑事都有。保留原貌供核對；民事分析請用正規化後的 `case_type_norm`／`case_type_category` |
| `judgment_type` | 判決／裁定／其他，由裁判字號結尾判斷 | 只分析判決時用來排除裁定 |
| `source_url` | 司法院網站上這份裁判書的網址 | 點開核對原文 |
| `keyword` | 第一次抓到這份裁判書的批次（搜尋關鍵字，或「臺灣臺北地方法院-民事-判決」這類自動標籤） | 追查資料來源。**只有一個值、之後被其他批次搜到也不會改，所以不代表判決內容**；依主題找判決請搜 `full_text` |
| `parsed_at` | 解析時間 | 確認這筆是何時、用哪一版程式解析的 |

### 當事人

多人時以全形分號「；」分隔。一審記在原告／被告，上訴審記在上訴人／被上訴人，
非訟的聲請人／相對人也記在原告／被告欄；刑事判決的被告記在被告欄。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `party_roles` | 所有當事人與稱謂，如「原告：甲；被告：乙、丙」 | 最完整的當事人紀錄，各種稱謂都不會漏 |
| `plaintiff` | 原告（或聲請人） | 一審與非訟案件的主動方 |
| `defendant` | 被告（或相對人） | 一審與非訟案件的被動方。除權判決沒有對造，所以本欄空白比例高是正常的 |
| `appellant` | 上訴人 | 上訴審的主動方（可能是原審任一造） |
| `appellee` | 被上訴人 | 上訴審的被動方 |
| `plaintiff_agent` | 原告方的代理人（含律師、法定代理人） | 判斷原告有無律師的來源（`plaintiff_has_lawyer`） |
| `defendant_agent` | 被告方的代理人（刑事判決為辯護人等） | 判斷被告有無律師的來源（`defendant_has_lawyer`） |
| `appellant_agent` | 上訴人方的代理人 | 上訴審判斷有無律師的來源 |
| `appellee_agent` | 被上訴人方的代理人 | 同上 |
| `other_parties` | 固定空白 | 解析程式從未實作，欄位保留只是為了資料表結構一致 |

### 判決內文段落

依判決書的段落標題切出來。民事判決的論理通常只寫在「理由」「事實及理由」「事實」
其中之一，三欄擇一有值是正常的。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `verdict` | 主文：法院的判決結論 | 最重要的段落。民事的勝敗、判准金額、訴訟費用分擔、假執行，以及刑事的罪名與刑度，都從這裡推導 |
| `facts` | 「事實」段（舊式寫法把事實與理由分開） | 論理內容的來源之一 |
| `reasons` | 「理由」段 | 論理內容的來源之一。刑事判決的「證據並所犯法條」也會併進來，**有時其實是附在簽名後的檢察官聲請書／起訴書全文**，做文字分析時請留意 |
| `facts_and_reasons` | 「事實及理由」合併段（民事簡易判決常見） | 論理內容的來源之一 |
| `criminal_facts` | 刑事判決的「犯罪事實」段 | 刑事分析用；民事判決幾乎都空白 |
| `conclusion` | 「結論」段，一律空白 | 「據上論斷」通常夾在段落中間而不是獨立標題，切不出來；內容已在 `reasons` 或 `facts_and_reasons`。欄位保留是為了資料表結構一致 |
| `applicable_laws` | 原始法條句：「判決如主文」前最後一個「依」之後的文字 | 只有約三分之一的判決有這種句型；分析請改用 `applicable_laws_json` |
| `full_text` | 裁判書全文 | 依主題搜尋判決（`LIKE '%借名登記%'`）、規則抽不到時回頭查原文 |
| `judges` | 原始法官欄，以全形分號「；」分隔 | 保留原貌；分析請用 `judges_json`／`presiding_judge` |
| `clerk` | 書記官 | 保留紀錄，目前沒有分析用到 |

### 結構化：案件分類

從這一節開始是 `structuring.py` 從上面的文字欄位推導出來的欄位（規則版本見 `structuring_version`）。
這套規則是為**民事判決**設計的。刑事判決也會套用，但結果沒有意義，刑事分類請以刑事組的規則為準。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `case_kind` | 字別：裁判字號中的「訴」「重訴」「簡上」「除」等 | 字別決定程序類型（一審、上訴、除權、非訟…），是分類的起點 |
| `case_kind_category` | 【民事】由字別歸納的層級：給付確認／非對審／上訴抗告／家事形成／裁定 | 決定該看哪個結果欄：給付確認類看 `outcome`，上訴抗告類看 `appeal_outcome`；非對審（除權判決等）不適合算勝訴率 |
| `case_type_norm` | 【民事】案由正規化：去掉「等」、統一寫法 | 把同一件事的不同寫法合在一起，方便依案由統計 |
| `case_type_category` | 【民事】案由大類（17 類，如侵權、金融借貸、契約、勞動） | 控制案件組合：不同案由的勝訴率天生不同，比較法官或法院時要以它調整 |
| `case_type_mid` | 【民事】案由中間分類（約 50 類，如「侵權：交通事故」「侵權：詐騙」「契約：工程與承攬」「勞動：資遣費」）。侵權案件依原告主張段落的關鍵字細分，其他大類依正規化案由細分；沒有細分規則的大類（金融借貸、不當得利…）沿用大類名稱 | 大類太粗：同樣是侵權的對審案件，詐騙被害人求償的勝訴率約八成，醫療糾紛約三成。用原告主張分類，不會把判決結果帶進來 |
| `party_posture` | 【民事】程序地位：第一審對審／非訟／上訴抗告／刑事（依當事人稱謂判定） | 區分案件的程序性質，和 `case_kind_category` 互相核對。出現「公訴人」「自訴人」「受刑人」稱謂時判為「刑事」，但不是每份刑事判決都判得出來，區分民刑事請看 `case_number` |

### 結構化：判決結果【民事】

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `outcome` | 訴訟結果：勝訴／一部勝訴一部敗訴／敗訴／分割類／確認勝訴／其他/不明確／非終局 | 主要的依變數。**只在 `case_kind_category = 給付確認` 時有值**，其他類別一律空白 |
| `main_outcome` | 本訴的結果 | 和反訴分開，避免反訴結果混入本訴的勝敗 |
| `counter_outcome` | 反訴的結果（沒有反訴則空白） | 單獨分析反訴 |
| `has_counterclaim` | 是否有反訴（1／0） | 篩選或排除有反訴的案件 |
| `appeal_outcome` | 上訴審結果：上訴駁回／原判決廢棄／一部廢棄 | 上訴抗告類案件的結果欄（`outcome` 在這類案件是空白） |
| `relief_type` | 主文判准的給付類型：金錢給付／非金錢給付／確認／形成／不作為（可複合） | 區分要不要看金額。**全部敗訴時主文只有「原告之訴駁回」，會判成「其他」** |
| `has_provisional_exec` | 主文是否有「得假執行」（1／0） | 程序特徵，可當控制變數 |
| `cost_share_plaintiff` | 訴訟費用由原告負擔的比例（0～1）。會讀完整句分擔（「餘由…負擔」「各負擔」「兩造各負擔」），分擔寫成金額而非比例時為空值 | 比 `outcome` 更精細的勝敗程度：同樣是一部勝訴，原告負擔 3% 和 97% 天差地別 |

### 結構化：金額【民事】

金額一律換算成整數元。分析金額前請先排除 `quality_flags` 有旗標的列，不要把空值當成 0。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `awarded_amount` | 判准金額：本訴各判項加總（不含反訴） | 判決結果的金額面。有「重複給付免責」旗標時**刻意留空**，因為加總會多算 |
| `awarded_currency` | 判准金額的幣別（TWD、USD…，多幣別以 `/` 連接） | 多幣別或外幣時不能直接和台幣加總比較 |
| `awarded_n_items` | 判准的判項數 | 看判准金額是由幾筆組成 |
| `awarded_items_json` | 每個判項的金額、幣別、原文與本訴／反訴 | 需要逐項檢查或分析反訴金額時使用 |
| `awarded_in_table` | 判項寫「如附表所示」（1／0） | 為 1 時金額在附表裡，`awarded_amount` 可能不完整 |
| `claimed_amount` | 原告請求金額 | 計算獲償比例的分母 |
| `claimed_currency` | 請求金額的幣別 | 與判准幣別不同時不計算比例 |
| `claimed_source` | 請求金額的來源：直接抽取／直接抽取（無聲明錨點）／直接抽取（不完整）／主文回推／未取得 | 判斷請求金額可不可信。「主文回推」是用判准金額代入的，拿來算比例是循環論證；「無聲明錨點」是找不到聲明段落、從全文開頭讀到的金額，可信度較低 |
| `grant_ratio` | 獲償比例（0～1）：全部勝訴＝1、敗訴＝0、一部勝訴＝判准 ÷ 請求 | 衡量法院准許了多少。來源見 `grant_ratio_source`；一部勝訴只在請求金額為「直接抽取」且幣別一致時計算 |
| `grant_ratio_source` | 獲償比例的來源：計算／全部勝訴／敗訴（空白＝沒有比例） | 「全部勝訴」「敗訴」是依判決結果定義的值，「計算」是判准 ÷ 請求。只想用實際金額算出的比例時，篩選「計算」 |

### 結構化：法條

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `applicable_laws_json` | 判決引用的法條清單，每條拆成法規、條、項、款（如 `民法§184第1項前段`） | 依法條統計、找請求權基礎。比原始的 `applicable_laws` 完整得多 |
| `law_n_citations` | 引用法條的數量 | 粗略反映論理的複雜度 |
| `law_primary` | 主要法規（只到法典名稱，如「民法」）：排除程序法後引用最多者 | 快速分類用；要到條文層級請看 `applicable_laws_json`。注意引用最多的條文常是遲延利息（民法§229、§233、§203）與連帶責任這類附帶條文，不等於請求權基礎 |
| `claim_basis_json` | 【民事】原告主張的請求權基礎：`{"articles": 條文…, "relations": 法律關係…, "groups": 請求權類型…}`。只從 `plaintiff_claim_text` 的「依…規定請求／提起」與「依…之法律關係」「依…契約」句子抽取，排除程序法與利息、遲延、連帶、債權讓與等附帶條文 | 對應刑事的「法條」。取自原告主張，判決前就存在，可以當預測變數 |
| `claim_basis_primary` | 【民事】原告援引的第一個條文，到「條」為止（如 `民法§184`）；只寫法律關係、沒寫條文時空白 | 條文層級的分析 |
| `claim_basis_group` | 【民事】主要請求權類型（約 25 類：侵權行為、消費借貸、不當得利、物權、勞動、買賣、承攬…）。先看條文所屬範圍，沒有條文時看法律關係；「其他契約」「其他」只在沒有更具體的類型時才用 | 比條文粗、比案由大類貼近法律依據。給付確認類約 83% 有值 |

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `judges_json` | 法官清單與角色（獨任／審判長／陪席） | 法官層級分析的基礎資料 |
| `judge_count` | 法官人數（大於 1 即合議庭） | 區分獨任與合議 |

### 結構化：當事人與程序特徵【民事】

這些是分析時的控制變數，用來區分「結果差異來自法官」還是「來自案件本身」。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `defendant_is_corp` | 被告是否為法人（1／0） | 公司或銀行當被告的案件性質不同。上訴抗告案件為空值，因為沒有「被告」可判斷 |
| `plaintiff_has_lawyer` | 原告方代理人是否為律師（1／0） | 控制變數。0 是「判決書上看不出代理人是律師」，不等於確定沒有律師 |
| `defendant_has_lawyer` | 被告方代理人是否為律師（1／0） | 同上。和一造辯論高度相關（被告沒到庭自然沒有律師） |
| `is_default_judgment` | 是否一造辯論判決（全文出現「一造辯論」） | 一造辯論幾乎都是原告全勝，分析勝敗時一定要分開看 |
| `reasoning_length` | 論理字數：`reasons`＋`facts_and_reasons`＋`facts` | 反映判決寫得多詳細（三段擇一撰寫，所以相加） |
| `plaintiff_claim_text` | 【民事】理由中的原告主張段落（已去除空白）。只對給付確認類民事判決切分 | 判決前就存在的文字，可以當文字模型的輸入。**找不到答辯起點時，答辯內容會併在這一欄**（對審案件約 12%），做文字模型時建議與答辯欄合併使用 |
| `defendant_defense_text` | 【民事】被告答辯段落；被告未到場時是「被告未於言詞辯論期日到場…」那句陳述 | 同上 |
| `court_reasoning_text` | 【民事】法院判斷段落（從「本院之判斷」「兩造不爭執事項」或答辯結束後的下一個段落編號開始） | 心證層（爭點、證據採信）只該從這一段抽取。**不能當預測勝敗的輸入**，裡面寫著判決結果 |
| `section_split_status` | 【民事】切分結果：成功／無原告主張標記／無法院判斷標記（空白＝不適用） | 切不出法院判斷時三欄一律留空，避免主張段落混入判斷。給付確認類約 98.5% 成功 |

### 使用注意事項

#### `grant_ratio`、`grant_ratio_source` 與 `claimed_source`

`grant_ratio` 依判決結果分三種情形，來源記在 `grant_ratio_source`：

| `grant_ratio_source` | 條件 | `grant_ratio` |
|---|---|---|
| 全部勝訴 | `outcome = 勝訴`，且主文有金錢給付 | 1 |
| 敗訴 | `outcome = 敗訴`，且聲明讀得到請求金額（確定是金錢請求） | 0 |
| 計算 | 其他情形（主要是一部勝訴）：`claimed_source = 直接抽取`、幣別一致、判准不大於請求 | 判准 ÷ 請求 |

全部勝訴和敗訴是依定義補值，不是用判准金額回推請求金額的循環論證：法院准許全部請求，
比例就是 1；全部駁回，比例就是 0。全部勝訴時即使能從聲明算出比值也以 1 為準——
全部勝訴卻算出小於 1，代表聲明金額抽多了（重複計算、抓到減縮前的舊聲明），不是法院少判。
舊版（規則 2.3.0 之前）敗訴是空值，平均只涵蓋至少判准一部分的案件，會高估獲償程度。

`claimed_source` 有五種值：直接抽取／直接抽取（無聲明錨點）／直接抽取（不完整）／主文回推／未取得。

- 「主文回推」是指訴之聲明寫「如主文所示」且全部勝訴時，用判准金額代入請求金額。
  **請求金額本身不能拿來分析**（例如當作預測勝敗的變數），因為它只出現在全部勝訴的案件。
- 「直接抽取（無聲明錨點）」是找不到「聲明：」等段落、退回全文開頭讀到的金額，
  常把事實敘述裡的多筆金額一起加總，不用來計算比例。
- 一部勝訴的比例仍可能有誤：聲明變更寫在別處（「變更聲明為後述」）、判項的連帶範圍
  重複計算等情形規則抓不到。需要精確值時請抽樣核對。

`cost_share_plaintiff` 是比 `outcome` 更精細的連續變數：主文只說「一部勝訴一部敗訴」，
但「訴訟費用由被告負擔 97%」和「負擔 3%」是天差地別的結果。

#### `plaintiff_has_lawyer`／`defendant_has_lawyer` 的兩個前提

- **`0` 的意思是「判決書上看不出代理人是律師」，不是「沒有律師」。**
  判準是拿代理人姓名回全文比對後方是否緊接「律師」；判決只寫「訴訟代理人 王大明」
  而未註明身分時會判 0。可以當控制變數，但不能當成律師代理率對外引用。
- **`defendant_has_lawyer` 與 `is_default_judgment` 高度相關。** 被告未到庭當然沒有律師，
  一造辯論案件的 `defendant_has_lawyer` 絕大多數是 0。兩欄不宜同時放進同一個迴歸。

#### `quality_flags` 的值

| 旗標 | 意義 | 分析時怎麼辦 |
|---|---|---|
| `金額於附表` | 金額寫在附表，正文抓不到 | 從金額分母排除，或人工補 |
| `非金錢給付` | 本來就沒有金額 | **不是缺漏**，從金額分母排除 |
| `定期給付` | 按月／按年給付，沒有總額 | 同上，本質上不存在總額 |
| `外幣`／`混合幣別未合計` | 非台幣或多幣別 | 不做匯率換算，單獨處理 |
| `判准與請求幣別不同` | 判准與請求的幣別對不上 | 不計算 `grant_ratio`，單獨處理 |
| `判准大於請求` | 聲明段落只抓到部分項目 | `grant_ratio` 已作廢，勿自行回推 |
| `重複給付免責` | 不真正連帶：主文分列數判項，但有「任一被告給付後其餘免責」條款，各判項是同一筆債務 | `awarded_amount` **刻意留空**（加總會憑空多一倍）；需要時看 `awarded_items_json` 自行判斷，勿逕行加總或去重 |
| `反訴金額未計入`／`僅反訴有給付` | 判准金額只算本訴，反訴另計 | 需要反訴金額時看 `awarded_items_json` |
| `金額抽取失敗` | 真正的抽取失敗 | 這才是需要改進規則的部分 |
| `無法條引用`／`無法官` | 上游解析缺漏 | 從相關分析排除 |

## crawl_records 表

爬蟲在結果清單頁看到一份裁判書、下載 HTML 後寫入一列；解析程式再依這張表找出尚未解析的檔案。

| 欄位 | 內容 | 用途／為什麼需要 |
|---|---|---|
| `id` | 紀錄編號 | `judgments` 表的 `crawl_id` 指向這裡 |
| `case_number` | 裁判字號 | 唯一識別；已存在的裁判書不會重複下載 |
| `court` | 法院，從裁判字號開頭擷取 | 爬取階段的法院資訊（`judgments.court` 是解析時重新取得的） |
| `case_title` | 案由，取自結果清單頁的「裁判案由」欄 | 下載前就知道的案由，通常和 `judgments.case_type` 相同 |
| `judgment_date` | 裁判日期，取自網址，西元 `YYYY-MM-DD` | 爬取階段的日期資訊 |
| `source_url` | 司法院網站上的網址 | 重新下載或核對原文 |
| `html_file` | 本機 `html_cache/` 裡的 HTML 檔路徑 | 重新解析（`--reparse`）時從這裡讀取，不必重爬 |
| `keyword` | 第一次抓到它的批次標籤 | 追查是哪次爬取抓到的；不代表判決內容 |
| `crawled_at` | 下載時間 | 追查爬取時間 |
| `parsed` | 是否已解析進 `judgments` 表（1／0） | `html_parser.py` 只處理 0 的列 |

## Datasette 使用提示

- `python browse_db.py` 後開啟 <http://127.0.0.1:8001>，Ctrl+C 結束。網頁是唯讀的。
- 表格太寬時，按住 Shift 滾動滑鼠滾輪可以左右捲動。
- 網址加上 `_col=欄位名` 只顯示指定欄位、`_nocol=欄位名` 隱藏欄位，`_size=10` 每頁筆數。
- 資料庫頁的表格只顯示「Many rows」是正常的：Datasette 只給每張表 5 毫秒計算筆數，
  點進表格頁就會顯示實際筆數。
- 依主題找判決請搜全文：`full_text LIKE '%關鍵字%'`，不要用 `keyword` 欄。
