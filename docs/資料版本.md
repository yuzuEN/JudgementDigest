# 資料版本

資料、資料集與模型檔都不進 repo（太大，且含當事人資訊），放在共用的雲端空間，以版本命名。
程式讀取的位置寫在 `config.py`，可以用環境變數改到自己的位置。

`judgments.db` 是 work 的超集：work 的每個 `id` 在正式資料庫裡都有，字號也相同。

**20261108 怎麼做的**（兩人各自做、結果相同）：把 20261014 複製一份改名成 `judgments.db`，在那個資料夾執行
`python data_pipeline/backfill_structured.py --no-backup`（先 `--dry-run` 看過統計），再改名。
兩邊跑下面這段，輸出都是 `2.5.1|183238|34104|753579954822.0|208232310761.0|67803.7659|33584|6612`：

```sql
SELECT structuring_version, COUNT(*),
       SUM(outcome = '一部勝訴一部敗訴'),
       ROUND(SUM(claimed_amount)), ROUND(SUM(awarded_amount)), ROUND(SUM(grant_ratio), 4),
       SUM(defendant_is_corp), SUM(relief_type = '非金錢給付')
FROM judgments GROUP BY structuring_version;
```

和 20261014 逐筆比對，改變的筆數都符合 10/26 的全庫比較，判決全文 0 筆改變。
用新庫重建 `text_dataset_v5.csv`，和原本的檔案逐位元相同（46,683 件）。

**20261112 怎麼做的**：同上，改從 20261108 複製（規則 2.5.2）。同一段 SQL 的輸出是
`2.5.2|183238|34104|753579954822.0|208232310761.0|67803.7659|34632|6612`（和 20261108 比，只有 `SUM(defendant_is_corp)` 從 33584 變成 34632）。
和 20261108 逐筆比對：所有結構化欄位與判決全文中，只有 `defendant_is_corp` 改了 1,374 筆（0→1 有 1,211 筆、1→0 有 163 筆；
一審對審 142,875 件中改了 1,353 筆，0.95%），其餘 0 筆改變。用新庫重建 `text_dataset_v5.csv`，和原本的檔案逐位元相同。
要確認自己回填的結果一樣，可以兩邊各跑：

```sql
SELECT defendant_is_corp, COUNT(*) FROM judgments GROUP BY 1;
-- NULL|14801（上訴審，不適用）、0|133805、1|34632
```

| 2.5.2（2026-11-12） | 併入同學的當事人解析 `data_pipeline/parties.py`：`defendant_is_corp` 改成從全文開頭的當事人欄重新解析被告，任一被告是公司團體或政府機關就是 1；解析不出被告時用原本的方法。全庫比對時補了 parties.py 的漏網（見下） | 已回填：`judgments_work_20261112.db`（2026-11-12）；`judgments.db` 尚未回填 |

- 2.5.1 對全庫（183,238 件）只改了約 127 件的金額與給付類型欄位（0.07%）。
- `text_dataset_v5.csv` 用 2.5.1 重建，和 2.5.0 逐格相同（46,683 件，每個欄位都一樣），所以 v5 與下面「重現檢查」的結果不受影響。
- 金額模型（`python -m civil.models.amount_service`）預設用目前的 `structuring.py` 在記憶體裡重新推導金額欄位（2.5.1），不寫入資料庫；`--rules db` 改讀資料庫裡的欄位（`structuring_version` 要全庫一致）。對 20261108 用 `--rules db` 和記憶體推導的結果完全相同；對 20261014（2.4.0）是 MAE 0.233 對 0.234。
- 已知還沒修的金額問題（各人名前的「各」、括弧明細重複加總、撤銷贈與的返還、擴張金額的利息部分）接下來處理；修完要再抽一批新樣本量正確率。
- 2.5.2 只改 `defendant_is_corp`：
  - **0→1（1,211 筆）**大多是舊規則漏掉的：祭祀公業、寺廟宮廟、獨資商號（小吃店、工程行、診所）、重劃會、同業公會、合作社、外國公司（LLC、PTE LTD）、國家中山科學研究院等。
  - **1→0（163 筆）**大多是舊欄位把不是被告的人算進去：受告知訴訟人、參加人、第三人、反訴被告，以及寫在被告後面的在監地址（「法務部矯正署…」）；另有「X即Y」的獨資商號與事務所（依最高法院 43 台上 601 算自然人）。
  - 全庫比對時在 parties.py 補的漏網（都有測試，見 `tests/test_parties.py` 的 `TestFoundInBackfill252`）：名稱中間的機關（「…市政府…大隊」「…檢察署檢察官」「…委員會…中心」「…署…隊」）、學校簡稱、機關擔任遺產管理人、名字後接的在監說明、「原居…」舊地址行、「原告即反訴／被告」稱謂斷行、名稱含門牌字的團體（「…10號大樓管理委員會」）。
  - 已知還有的錯：當事人欄格式特殊時偶爾漏掉某位公司被告（抽樣 1→0 的 20 筆裡約 4 筆），名稱被截斷的私立學校（「…高級中學附」）。
- **模型還沒有用到 2.5.2**：勝敗、金額模型的 `defendant_is_corp` 讀的是 `analysis_fields.pkl`（見下），不是資料庫，所以這次換庫不影響任何模型與 v5 資料集。改由資料庫算樣本母體與結構化變數（v6）時才會用到，到時候勝敗、金額、Base 模型一起重訓。

### `analysis_fields.pkl`（建資料集的輸入）

決定 v5 的樣本母體（A2 對審樣本），也是結構化變數（律師、法人、反訴、請求權、程序）的來源（`config.FIELDS_PKL`）。
它是在 repo 改結構前，由三步本機程式產生的，**目前當作固定的輸入資料**，不在 repo 裡重新產生：

```
judgments_snapshot_20261013.db（10/13 快照，規則 2.3.0）
  → sensitivity_analysis/src/rederive.py   用 2.4.0 重算 → rederived_2.4.0.db
  → field_validation/src/build_fields.py    → analysis_fields.pkl（102,328 件）
```

欄位是 2.3.0 與 2.4.0 的混合（判決結果用 2.4.0 重算，其他沿用快照），細節見各分析報告。
下一版（v6）改成直接從分析資料庫（目前是 20261112，規則 2.5.2）算樣本母體與結構化變數，就不再需要這個檔案。

## 上線用的模型與檢索資料

都在 `artifacts/`（`config.ARTIFACTS_DIR`），不進 repo。民事的兩個模型放在 Hugging Face 的私人 repo `JudgementDigest/judgementdigest-artifacts`，用 `bash scripts/sync_civil_models.sh` 下載（見 [civil/README.md](../civil/README.md)）；檢索資料由組內另外分享。也可以用下面的指令自己產生：

| 資料夾 | 怎麼產生 | 大小 | 內容 |
|---|---|---:|---|
| `civil_winloss_v1/` | `python -m civil.models.service train` | 9 MB | 勝敗模型（`scikit-learn` 要和訓練時同版本才讀得出來，見 `backend/requirements.txt`） |
| `retrieval_civil_v3/` | `python -m retrieval.build`（要有 `judgments.db`，約 35 分鐘） | 2.5 GB | 檢索索引、遮名後的案件清單與判決段落，158,327 件 |
| `civil_amount_v1/`（選用） | `python -m civil.models.amount_service train`（約 2 分鐘） | 8 MB | 獲償比例模型：若為一部勝訴，判准金額占請求金額的比例（10%–90% 範圍）。沒有這個資料夾時，金額範圍退回相似判決的分位數。`meta.json` 記各案由的訓練件數、損害子項目關鍵字、請求金額的範圍；2026-11-11 以前訓練的舊檔沒有這些欄位，後端不會用，要重新訓練。要用 `backend/requirements.txt` 鎖定的 `scikit-learn` 版本訓練 |

資料不進 Git，所以用下面的方式對回版本：

- `meta.json` 記錄 Git commit、規則版本、來源資料庫的件數與修改時間
- 分享的壓縮檔名稱帶版本與日期（例如 `retrieval_civil_v3_20261105.zip`），發布後不覆蓋，有改動就出新版
- 每一版在下表記一行

| 版本 | 日期 | 來源 | 規則 | 件數 | 差異 |
|---|---|---|---|---:|---|
| `retrieval_civil_v1` | 2026-10 | 文字資料集 v5 | 2.4.0 段落 | 46,683 | 第一版 |
| `retrieval_civil_v2` | 2026-11-05 | `judgments.db`（236,009 件） | 2.5.0 | 158,327 | 納入簡易庭與一造辯論，分統計、列表兩層 |
| `retrieval_civil_v3` | 2026-11-05 | 同 v2 | 2.5.0 | 158,327 | 語料相同，加強第三人姓名的遮名 |

勝敗模型的 5 折評估（`python -m civil.models.service evaluate`，v5，46,683 件）：

| 模型 | 勝訴 precision | 勝訴 recall | 敗訴 precision | 敗訴 recall | 校準誤差（ECE） |
|---|---:|---:|---:|---:|---:|
| 只用原告主張 | 0.729 | 0.815 | 0.660 | 0.543 | 0.033 |
| 原告主張＋特徵（平台用這個） | 0.733 | 0.811 | 0.659 | 0.553 | 0.021 |
| 只用特徵 | 0.661 | 0.818 | 0.571 | 0.367 | 0.010 |
| 同一個模型，法院不知道 | 0.735 | 0.808 | 0.658 | 0.559 | 0.023 |
| 同一個模型，特徵都不知道 | 0.714 | 0.836 | 0.666 | 0.494 | 0.045 |

機率 50% 以上算判勝訴。問卷特徵對 precision、recall 的影響不大，主要改善校準。這些數字是用法官整理過的原告主張測的；民眾自己寫的描述見 `retrieval/README.md` 的口語測試，還沒有真人實測。
